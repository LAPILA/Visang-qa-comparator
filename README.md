# Web QA Comparator

## 프로젝트 설정 DB

프로젝트와 환경 목록은 로컬 PostgreSQL에 저장합니다. 프로젝트 루트의 `.env`에 `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`를 설정하고 `setup_windows.bat`로 의존성을 설치한 뒤 `run_windows.bat`를 실행하세요. 프로젝트 설정 화면을 처음 열면 필요한 두 테이블을 생성합니다. 기존 브라우저 저장소의 프로젝트는 설정 화면에서 처음 불러올 때 DB로 옮깁니다. 검사 규칙과 로그인 ID 기억 기능은 아직 브라우저 저장소를 사용합니다.

프로젝트의 각 환경에는 로그인 페이지 URL·ID·비밀번호를 선택적으로 등록할 수 있습니다. 비밀번호는 DB에 암호문으로 저장하고 API 응답에는 포함하지 않습니다. 첫 비밀번호 저장 때 `.env`에 `QA_CREDENTIAL_KEY`가 생성됩니다. 이 키를 잃으면 DB의 저장된 비밀번호를 복호화할 수 없습니다. 프로젝트 공유 SQL에는 로그인 정보가 포함되지 않습니다. 등록만으로 자동 로그인이 실행되지는 않습니다.

단일 환경 검사, 두 환경 비교, 과거 실행과의 회귀 비교, 조건 기반 UI 검사를 수행하는 **로컬 QA 워크스페이스 v0.3.1**입니다. Python, Playwright, Pillow와 기존 HTML/JavaScript UI를 사용하며 URL 매핑·영역별 화면 비교·HTTP/JavaScript 관찰·등록된 기능 시나리오의 기존 코드를 확장했습니다.

실사이트에는 승인한 경로·요소·기대값 설정이 필요합니다. 검색·입력·history 기능 시나리오는 공개 가능한 합성 데모에 등록되어 있고, 조건 계약은 사용자가 지정한 실사이트의 DOM에도 적용할 수 있습니다. 현재 지원 범위와 검증 결과는 [구현 현황](docs/IMPLEMENTATION_STATUS.md), 운영 절차는 [운영 안내](docs/OPERATIONS.md), 개발자 계약은 [결과 계약](docs/RESULT_CONTRACT.md)을 보세요.

## 시작하기

Python 3.10 이상이 필요합니다. 개발 검증 환경과 고정 라이브러리는 `requirements.txt`와 구현 현황에 기록합니다.

Windows에서는 `setup_windows.bat`를 한 번 실행해 가상환경·의존성·Chromium을 설치한 다음, `run_windows.bat`를 실행하세요. 기본 주소는 **[http://127.0.0.1:3000](http://127.0.0.1:3000)**입니다. 서버는 loopback에만 바인딩합니다.

직접 실행하려면:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe app.py
```

macOS/Linux에서는 `.venv/bin/python`을 사용합니다. 포트 변경은 `PORT` 환경변수, 로컬 결과 폴더 변경은 `QA_RUNS_DIR` 환경변수로 가능합니다. WindowsApps Python 별칭만 있는 경우 실제 Python을 설치하세요. 제공 스크립트는 `.venv` 또는 설치된 Python 실행 파일을 찾습니다.

## 먼저 합성 데모 실행

1. 환경에서 **합성 데모**를 선택하고 담당자를 입력합니다.
2. 기본 설정으로 검사를 시작합니다. 앱 안의 A/B 데모에만 접속하며 외부 요청이 필요하지 않습니다.
3. 페이지/영역별 결과를 열어 매칭 근거, 검증식, 스크린샷, 발견·차단된 행동을 확인합니다.
4. 상태·차이율·비교 불가·영역·검색 필터로 범위를 좁히고 검수 사유를 저장합니다.
5. 실행 이력에서 다시 열거나 CSV/JSON을 내려받습니다. 앱 재시작 후에도 결과와 검수 이력이 남습니다.

데모에는 의도적으로 **B의 필수 Help 버튼 누락**, **서버별 공지 내용 차이**, **`.do` 경로 차이**, **절대 실행하면 안 되는 저장/삭제 함정**이 들어 있습니다. 따라서 모든 행이 PASS인 것이 데모의 정답이 아닙니다. `/demo/meta`는 합성 정답 라벨과 함정 실행 횟수를 제공합니다.

## 네 가지 테스트 목적

| 목적 | 실제 실행 | 사용 시점 |
|---|---|---|
| 환경 비교 QA | A/B를 각각 검사하고 승인된 페이지·영역을 비교 | 운영↔STG, 개발1↔개발2 |
| 단일 환경 QA | A만 방문해 HTTP/JS·필수 영역·등록 시나리오를 검사 | 개발 서버 하나의 상태 확인 |
| 회귀 테스트 | 현재 A를 새로 검사하고 선택한 과거 실행과 비교 | 신규·반복·해결 후보·미재검 구분 |
| 조건 기반 UI QA | A의 현재 화면에서 조건·기대값 계약을 검사 | 긴 제목·빈 목록·페이지네이션 등 |

테스트 목적과 검사 모드(통합/시각/발견)는 별도로 저장합니다. 단일 환경·회귀·조건 기반 검사는 B 서버에 접속하지 않습니다. 회귀는 버전·범위·브라우저 조건이 맞는 실행끼리 평가하며, 누락되거나 차단된 검사를 해결로 취급하지 않습니다. 과거의 A/B 비교 실행을 단일 환경 실행과 동일한 범위로 간주하지 않습니다.

**같은 시작 페이지의 URL이 다른 경우:** 환경 비교에서 기본으로 선택된 ‘입력한 A/B 시작 URL을 같은 기능 페이지로 비교’를 사용합니다. 예를 들어 A `/#/`와 B `/`는 제목이나 최종 리다이렉트 경로가 달라도 입력한 두 시작 레코드끼리 한 행으로 연결합니다. 다른 탐색 페이지와 `#/notice`·`#/search`, 다른 상세 ID는 이 규칙으로 합치지 않습니다. 명시적 alias가 있으면 alias를 우선합니다. 실제 화면 준비·오류 관찰은 매칭과 별도로 판정합니다.

**차이율이 ‘미계산’인 경우:** ‘탐색만’ 모드는 URL·동작·오류를 발견하고 픽셀 비교를 하지 않습니다. 기존 실행의 ‘이 실행 설정으로 화면 비교 준비’에서 설정을 복원한 뒤 화면 검사로 새 실행을 시작하세요. 과거 보고서의 상태·모드는 바꾸지 않습니다.

조건 검사는 `visible`, `count`, `text_length`, `overflow`, `attribute`를 지원합니다. 화면이나 DB를 변경하거나 임의 JavaScript를 실행하지 않습니다. `long_title`, `empty`, `pagination` 사례는 데이터 전제조건이 필수이며 충족하지 못하면 BLOCKED입니다. 예시:

```json
[
  {
    "id": "notice.empty.message",
    "case": "empty",
    "url_pattern": "/notice*",
    "preconditions": [{"selector": ".notice-row", "kind": "count", "expected": {"equals": 0}}],
    "selector": "#empty-message",
    "kind": "visible",
    "expected": true
  }
]
```

위 선택자는 형식 예시입니다. 운영 DB에 데이터를 생성하지 않으며 조건에 맞는 URL·테스트 데이터를 먼저 준비해야 합니다. mock 응답 주입·DB 검증을 수행했다고 표시하지 않습니다.

## URL 구조가 다른 환경의 페이지 목록 만들기

제품과 환경을 분리합니다. 네 제품별 운영·STG·바이브 개발·레거시 개발 **16개 등록 주소** 중 A/B를 선택하면 URL이 채워집니다. 직접 입력과 환경 이름 변경도 가능합니다. `stg-`/`dev2-`/`-dev` 등을 일괄 제거하거나 다른 호스트를 추측하지 않습니다. [등록표](docs/ENVIRONMENT_URLS.md)에 제공 주소와 보존 규칙을 정리했습니다.

**탐색만 → 환경 내부 읽기 전용 링크 탐색 → 실행 → 환경별 페이지 목록·매칭 후보 검수 → 매핑 JSON에 추가 → 화면/통합 새 실행** 순서로 사용할 수 있습니다. 안전한 같은 출처 링크를 한도 안에서 탐색하고, 다른 URL이라도 메뉴 경로·폼·버튼·구조가 대응하면 REVIEW 후보로 연결합니다. 공통 템플릿만 같은 페이지나 서로 다른 상세 ID는 강제로 합치지 않습니다.

페이지 목록은 별도 CSV, 전체 근거는 JSON에 저장합니다. 후보를 추가해도 현재 보고서와 자동 상태를 바꾸지 않습니다. [환경 탐색·매핑 안내](docs/ENVIRONMENT_DISCOVERY.md)에 절차·범위·인터페이스를 정리했습니다.

등록 시나리오 `demo.search`, `demo.input_length`, `demo.history`는 검색(버튼/Enter/결과 없음), UTF-16 기준 10자 입력 경계, 목록→상세→뒤로가기·새로고침을 검증합니다. 이 기대값을 실제 회사 사이트의 요구사항으로 적용하지 않습니다.

## 실사이트 설정

네 제품에 운영·STG·바이브 개발·레거시 개발 주소를 모두 등록했습니다. 중고등 모바일 STG는 사용자 확인 주소 `https://stg-mv.vivasam.com/`입니다. 운영 모바일은 `/`, 레거시 모바일은 `/#/`로 구분하며, PC의 제공된 `/main`도 보존합니다. 주소 등록과 실제 사이트 접속·로그인·기능 검증은 별개이며 이번 개발 테스트는 합성 환경만 사용했습니다.

- 최초 URL과 명시적으로 매핑한 경로, 고급 설정의 허용 경로만 자동 방문합니다. 다른 링크는 발견 목록과 차단 사유에 남습니다.
- `#/...` route와 의미 있는 query 순서를 보존합니다. `.do`를 일괄 제거하지 않습니다. 구조 유사 후보는 REVIEW이며 승인 매핑으로 확정합니다.
- 허용 호스트는 정확한 `host[:port]`를 입력합니다. 외부 CDN/인증 호스트가 차단되면 결과의 `POLICY_BLOCKED`와 누락 범위를 확인한 후 필요한 호스트만 추가합니다.
- 정적 CDN은 별도 `resourceHosts`에 입력합니다. GET/HEAD의 script/stylesheet/image/font/media만 허용하며 해당 호스트로 이동하거나 XHR/fetch/POST를 허용하지 않습니다. 초등 모바일의 확인된 jQuery/Kakao SDK/공통 이미지 호스트는 이 별도 목록에 기본 등록되어 있습니다. 추적·광고 호스트 전체를 자동 허용하지 않습니다.
- 자동 POST/업무 변경/다운로드/알 수 없는 버튼은 기본 차단합니다. DOM 클릭 성공만으로 기능 정상 PASS를 만들지 않습니다.
- 현재 `safeActions`는 승인된 click 실행만 제공합니다. 행동의 정식 기대값 검사는 Python 시나리오로 확장해야 합니다.

고급 매핑 예시(실제 사이트 설정이 아닌 형식 예시):

```json
[
  {"baseline": "/old/notice.do", "candidate": "/new/notice", "page_class": "notice.list"}
]
```

영역 설정 예시:

```json
[
  {"id": "home.navigation", "selector": "#site-nav", "required": true, "mask_selectors": []},
  {"id": "home.notice", "selector": "#notice-list", "required": true, "mask_selectors": [".notice-title"]}
]
```

selector는 대상 화면에서 확인해야 합니다. 마스크가 데이터값 차이를 가려도 영역의 존재/가시성 검사는 수행합니다. 현재는 일반적인 텍스트 겹침·잘림을 전부 판정하는 엔진이 없으므로 마스크만으로 UI 정상이라고 결론내리지 않습니다.

## 로그인과 두 사람의 작업

**수동 로그인**을 선택하면 실제 Chromium 창이 열립니다. 각 환경에서 사용자가 직접 로그인하고 앱에서 계속을 누릅니다. 비밀번호·세션 파일을 API나 디스크에 저장하지 않으며, 세션은 해당 실행의 환경별 context에만 유지됩니다. 로그인 성공·권한 역할은 사용자가 확인해야 합니다. 일반 사이트에 대한 자동 인증 성공 판별은 아직 없습니다.

아이디 기억은 선택 기능입니다. 체크한 경우에만 현재 브라우저의 localStorage에 담당자/프로필/A·B별 ID를 저장합니다. 비밀번호 저장·자동 붙여넣기는 없습니다. 브라우저 저장값은 암호화된 OS 비밀 저장소가 아니므로 공용 PC에서는 사용하지 말고 지우기 기능으로 제거하세요.

두 사람은 담당자 이름으로 실행·검수를 구분합니다. 검수 저장은 revision으로 충돌을 검출하며 자동 판정은 덮어쓰지 않습니다. 사유와 기존 이슈의 http(s) URL을 검수 이력에 기록할 수 있습니다. 외부 이슈를 자동 생성하지 않습니다. **한 서버에서 동시 실행은 1개이며, 같은 결과 폴더의 중복 서버 실행도 차단**합니다. 각자 로컬 실행할 경우 결과 폴더와 브라우저 세션을 분리하세요. 담당자 문자열은 사용자 인증 기능이 아닙니다.

## 판정과 저장

| 상태 | 의미 |
|---|---|
| PASS | 실제 실행한 검증식의 기대값 충족 |
| FAIL | 명시한 기대값 위반 또는 현재 오류 정책의 실패 관찰 |
| DIFF | 승인된 매칭과 준비 조건에서 차이를 확인했지만 버그 여부 미확정 |
| REVIEW | 매칭·준비·기대값 등 판단 근거 부족 |
| SKIP | 설정·범위·안전 정책상 제외 |
| BLOCKED | 인증·데이터·선행 검사·실행 한도로 수행하지 못함 |
| ERROR | 브라우저·수집·비교·실행기 오류로 판정 불가 |

차이율 필터는 조회 범위만 바꿉니다. 0%와 비교 불가(null)를 구분하고, FAIL/ERROR는 별도 요약에도 남깁니다. 400/401/403은 일괄 무시하지 않으며 현재 정책은 출처·resource type을 구분합니다. endpoint별 예상 인증 응답 계약은 후속 작업입니다.

도구의 정책 차단 이후 발생한 JS·콘솔 오류는 `TEST_INFRA/POLICY_INTERFERENCE`로 구분하고 원시 메시지·관련 차단 요청과 함께 REVIEW로 표시합니다. 시간상 전후 관계만으로 정책이 원인이라고 확정하지 않습니다. 요청의 ERR_ABORTED도 실제 연결 장애로 단정하지 않으며 실행기가 닫으면서 취소한 요청만 별도 SKIP입니다.

발견 사항에는 HTTP/NETWORK/JAVASCRIPT/API/RESOURCE/NAVIGATION/STRUCTURE/FUNCTIONAL/VISUAL/DATA/AUTH/TEST_INFRA 분류를 적용합니다. 분류 사전의 존재가 모든 세부 항목의 자동 탐지를 의미하지 않습니다. 원시 관찰 수·결과 행 수·중복을 묶은 발견 사항 수·연결 이슈 수를 따로 표시하며, 같은 증거가 페이지와 영역에 함께 표시되어도 두 번 세지 않습니다. 고유 발견 사항도 검수 전에는 고유 제품 결함 수가 아닙니다.

`runs/<run-id>/report.json`에 실행 설정·결과·검수 이력, `a/`, `b/`, `diff/`에 PNG가 저장됩니다. 실행 중 앱이 종료되면 다음 시작 시 해당 run을 `PROCESS_INTERRUPTED` 오류로 표시합니다. 결과 폴더는 `.gitignore`에 포함됩니다. URL 인증 파라미터·일부 로그 문자열을 제거하지만 모든 개인정보를 자동 탐지하는 기능은 아니므로 실제 서비스 증거를 공개하기 전 검수해야 합니다.

신규 결과는 스키마 2.0입니다. 기존 1.x 결과는 원래 판정 그대로 열며 REVIEW/SKIP을 일괄 변환하지 않습니다. 저장 실패 시 실행을 ERROR로 표시하고 현재 서버의 메모리 결과를 JSON으로 내려받을 수 있게 유지합니다. 프로세스가 종료된 뒤 저장되지 않은 메모리 결과는 복구할 수 없습니다.
