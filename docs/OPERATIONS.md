# 로컬 QA 운영·인수 절차

기준일: 2026-11-03 KST. 이 문서는 현재 v0.2의 **로컬 실행** 운영 절차다. 실제 회사 사이트 전체의 검증 완료나 인증된 다중 사용자 서비스를 의미하지 않는다.

## 1. 시작·종료

1. README의 setup으로 고정 의존성과 Chromium을 설치한다. `run_windows.bat` 실행 후 `http://127.0.0.1:3000`을 연다.
2. 합성 데모로 환경 비교를 실행해 B 필수 Help 누락, 정상 데이터 차이 제외, 저장·삭제 함정 0건을 확인한다.
3. 실행 이력에서 보고서를 다시 열고 JSON/CSV와 이미지가 조회되는지 확인한다.
4. 실행 종료는 먼저 UI에서 중단하고 정리 완료 후 서버를 종료한다. 비정상 종료 실행은 다음 시작에서 PROCESS_INTERRUPTED로 구분한다.

PORT는 로컬 포트, QA_RUNS_DIR은 결과 저장 폴더다. 같은 폴더의 서버 중복 실행은 OS 파일 잠금으로 막는다. 폴더를 직접 삭제하거나 실행 중 복사·교체하지 않는다. 잠금은 종료 시 운영체제가 해제하므로 잠금 파일이 남아 있다는 이유로 강제 삭제할 필요가 없다.

## 2. 실사이트 프로필 준비

대상 QA와 제품별 다음 계약을 확정한 뒤 작은 범위부터 실행한다.

- 동일 제품·PC/모바일 구분, A/B 시작 URL, 알려진 대상 build ID.
- 테스트 계정 역할, 로그인 완료 판단, 세션 만료 표시. 현재 수동 로그인의 성공·역할은 사용자가 확인한다.
- 이동 경로와 API/CDN/SSO의 정확한 호스트. 자동 POST는 기본 차단이므로 필요한 조회 POST는 정식 어댑터가 추가되기 전 검사 불완전으로 남을 수 있다.
- 같은 기능의 URL 별칭, 각 영역 선택자, 필수/선택 구분, 동적 데이터 마스크.
- 실제 검색·입력 길이·history·팝업·다운로드의 기대값과 승인된 입력. 일반 click 성공을 기능 PASS로 사용하지 않는다.

첫 실행은 페이지·동작 예산을 작게 잡고 발견 목록과 차단 사유를 검수한다. 허용 범위를 넓힐 때는 목적과 안전 근거를 다른 담당자가 확인한다. 무조건 모든 버튼을 클릭하거나 전체 경로를 승인하지 않는다.

## 3. 두 담당자의 반복 작업

| 단계 | 담당 A: 핵심 엔진 | 담당 B: 명세·시나리오·검수 |
|---|---|---|
| 준비 | 버전·예산·관찰·저장·페이지 identity 확인 | 요구사항·선택자·데이터 조건·허용 동작 확인 |
| 실행 | 오류·차단·불완전 범위 조사 | 담당자와 테스트 목적을 지정해 검사 실행 |
| 검수 | 수집기/비교기 오류와 제품 오류 구분 | 기대값·실제값·A/B 증거·회귀 근거 확인 |
| 이슈 | 재현 가능한 입력·환경·버전 제공 | 확정 결함에 기존 이슈 URL과 사유 연결 |
| 재검 | 같은 계약으로 새 실행, 이전 결과 보존 | 해결 후보를 직접 검수하고 VERIFIED_OK 또는 재검 요청 |

한 서버의 실행 worker는 하나다. 두 사람의 검수는 revision으로 충돌을 검출한다. 두 PC에서 실행한다면 각자 결과 폴더를 사용하고 보고서를 구분한다. 담당자 이름은 자기 신고 정보이며 로그인·권한 시스템이 아니다.

## 4. 판정 검수 순서

1. 실행이 끝났는지와 별개로 manifest.status/coverage의 PARTIAL·미실행·차단을 확인한다.
2. FAIL/ERROR를 먼저 확인하고 필수 BLOCKED를 해결한다. 차이율 필터가 치명 항목을 숨기지 않는지 별도 목록을 확인한다.
3. DIFF는 실제 차이, REVIEW는 판단 근거 부족이다. 정상 배포 변경·서버별 데이터 차이와 버그를 QA가 구분한다.
4. 페이지·영역 행 수, 원시 관찰, 중복을 묶은 발견 사항, 확정 이슈를 서로 다른 지표로 기록한다.
5. 검수 사유와 담당자를 저장한다. 중요한 매핑·정책 예외·결함 판정은 상대 담당자가 교차 확인한다.
6. 회귀의 RESOLVED_CANDIDATE는 같은 검증식의 PASS 증거가 있는 후보일 뿐이다. 외부 이슈를 자동으로 닫지 않는다. NOT_RETESTED/NON_COMPARABLE은 해결로 보고하지 않는다.

## 5. 실패·복구

| 현상 | 처리 |
|---|---|
| 다른 서버가 결과 폴더 사용 중 | 기존 서버 상태 확인 후 종료하거나 QA_RUNS_DIR 분리. 실행 중 잠금 우회 금지 |
| 비정상 종료 | 재시작하여 PROCESS_INTERRUPTED 확인. 남은 PNG를 모두 정상 결과로 간주하지 않음 |
| 저장 실패 | ERROR 확인 후 서버를 종료하기 전에 JSON 다운로드. 저장되지 않은 메모리는 종료 후 소실 |
| 검수 HTTP 409 | 새 결과를 열어 상대 변경 확인 후 최신 revision에서 재검수 |
| 스크린샷/이미지 처리 오류 | ERROR 원인 확인 후 새 실행. null을 0%로 변경하지 않음 |
| 마스크가 영역 전체를 덮음 | BLOCKED/NO_COMPARABLE_PIXELS. 마스크 범위 검토 |
| 회귀 NON_COMPARABLE | reasons의 버전·규칙·범위·캡처 차이 확인. 비교 가능하도록 새 기준 실행 |
| 데이터 조건 미충족 | BLOCKED 유지. 해당 조건의 승인된 테스트 데이터·URL 준비 후 재실행 |

수집 중 프로세스가 완전히 종료되면 아직 반환되지 않은 check의 스트리밍 checkpoint는 없다. 저장된 manifest/보고서와 남은 증거 범위만 사용한다. 결과 폴더 백업·보존 기간은 팀에서 정하고 실행 중이 아닐 때 적용한다.

## 6. 배포·포트폴리오 인수 기준

- `python -B scripts/run_tests.py`와 `node --check public/app.js`를 통과한다. 브라우저 테스트가 SKIP되면 통과 개수와 별도로 표시하고 원인을 해결한다.
- 네 가지 목적·7상태·선행조건·CSV 0/null·검수 충돌·재시작·안전 함정·화면 반응형을 합성 환경에서 재현한다.
- 실제 사이트 결과의 탐지율·오탐률·속도는 라벨링한 대상과 측정 로그가 있을 때만 발표한다. 합성 성과를 실서비스 성과로 바꾸어 적지 않는다.
- CI 파일의 존재와 GitHub Actions의 실제 실행 성공을 구분한다. 커밋·푸시는 사용자가 수행한다.
- 공개 자료에는 합성 증거를 사용한다. 회사 소스·계정·공지/자료·세션·실서비스 이미지는 별도 검수 없이 공개하지 않는다.

팀의 로컬 QA 도구로 사용하는 범위와 공용 서비스 배포는 구분한다. 네트워크 공동 운영을 위해서는 사용자 인증·역할·접근 기록, HTTPS, 공유 저장소 transaction, 증거 암호화·보존 정책, 백업/복구와 부하 검증이 추가로 필요하다. 현재 서버는 loopback 바인딩을 유지한다.
