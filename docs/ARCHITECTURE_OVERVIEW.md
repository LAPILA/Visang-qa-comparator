# VISANG QA AI · 구조 설명 (소개·발표용)

기준일: 2026-11-05 · v0.4.0 · 규칙 v2.3

## 한 줄

두 환경의 웹 서비스를 **자동 로그인 → 자동 탐색 → 관찰·캡처 → 비교 → 판정 → 검수 분류**까지 한 파이프라인으로 돌리고, 모든 판정에 근거(스크린샷·HTTP·JS 로그)를 붙여 사람은 *이슈 / 대인체크 / 재검*만 결정하게 하는 로컬 QA 워크스페이스.

## 파이프라인

```
설정(프로필·A/B URL·범위) ─▶ 1 진입 ─▶ 2 탐색 ─▶ 3 관찰 ─▶ 4 기능 ─▶ 5 비교 ─▶ 6 판정 ─▶ 7 검수 분류 ─▶ UI/CSV/JSON
                             로그인    읽기 링크   HTTP/JS   시나리오   매칭+     7상태     이슈/대인체크/
                             커버 통과  정책 필터   캡처      조건·스모크 Pillow    발견 분류  재검/정상
```

| 단계 | 하는 일 | 코드 | 상태 |
|---|---|---|---|
| 1 진입 | 테스트 계정 자동 로그인(선택자 없으면 로그인 링크 → 비밀번호 입력란 → 아이디 입력란 자동 탐지). 자격증명은 PC의 `secrets/accounts.json`·환경변수만. 커버/랜딩 페이지(`/#/coverPage`) 버튼 한 번 통과 | `qa/secrets.py`, `qa/engine.py:_test_account_login/_find_login_form/_apply_entry_action` | 완성 |
| 2 탐색 | 시작 페이지부터 같은 출처의 읽기 링크를 페이지·깊이·동작·시간 한도 안에서 따라감. 회원가입·계정·마이페이지·쓰기 경로·POST 폼·다운로드·API는 정책으로 제외 | `qa/policy.py`, `qa/engine.py:_crawl/_network_guard` | 완성 |
| 3 관찰 | 페이지마다 HTTP 응답, 콘솔·JS 오류, 깨진 이미지, 네트워크 실패, 차단 요청 수집. 실사이트 프로필은 완화 모드: 이 관찰은 "기타 로그"로 남기고 판정에서 제외 | `_attach_observers`, `observation_mode` | 완성 |
| 4 기능 | (a) 등록 시나리오 — 기대값 있는 기능 검증 (b) 조건 계약 — visible/count/text_length/overflow/attribute (c) 스모크 클릭 — href 없는 버튼을 눌러 "출처 유지·새 JS 오류 없음·응답 유지" | `qa/scenarios.py`, `qa/conditions.py`, `_smoke_actions` | **부분**: 시나리오는 합성 데모 3개뿐, 실사이트 기대값 미등록 |
| 5 비교 | **짝 우선 탐색**: A를 먼저 돌고, B는 A가 실제로 방문한 라우트를 B 호스트로 옮겨 먼저 방문한 뒤 자기 링크 탐색(호스트가 다르고 시작 라우트가 같을 때). A/B 페이지 짝짓기: 명시 별칭 → 선택 시작쌍 → 동일 라우트 → 동등 라우트(`/`·`/#/`·`/main`·`.do`) → 의미 후보(검토). 짝지어진 페이지·영역을 Pillow로 픽셀 비교(마스크·임계값) | `qa/matching.py`, `qa/comparison.py`, `_result_rows` | 완성 |
| 6 판정 | 검증식을 7상태(PASS/FAIL/DIFF/REVIEW/SKIP/BLOCKED/ERROR)로 결정론 집계. 발견 사항을 분류·중복 제거해 고유 발견 수 산출 | `policy.aggregate_status`, `qa/findings.py` | 완성 |
| 7 검수 분류 | 이슈 등록 후보 / 대인체크 / 재검 / 정상 / 미실행 + 제안 검수 상태. 검수 이력(revision)·회귀 비교(신규/재발/해결 후보) | `qa/triage.py`, `qa/store.py`, `qa/regression.py` | 완성 |

## 설계 원칙 (질문 대비)

1. **안전 수준이 정책을 결정한다** → `strict`: 변경·결제·탈퇴·다운로드는 이름만 봐도 차단, 승인 동작·시나리오·스모크(명시 `type=button`)만 실행. `test_account`: 테스트 계정이 할 수 있는 쓰기·폼 제출·마이페이지까지 실행하되, 공용 계정을 망가뜨리는 회원탈퇴·비밀번호·로그아웃·결제·회원가입은 어느 수준에서도 차단.
2. **클릭 성공 ≠ 기능 PASS.** 기대값 없는 클릭은 대인체크로 남긴다. 스모크 PASS는 "안 터짐"의 증거이지 기능 정상의 증거가 아니다.
3. **DB 데이터 차이는 버그가 아니다** → 시각 DIFF·데이터 분류는 대인체크. 마스크로 동적 영역을 가리면 줄어든다.
4. **오류 로그는 판정이 아니라 증거** → 콘솔·리소스·네트워크 관찰은 "기타"로 접어 두고, 페이지 자체 오류·기능 계약 위반만 FAIL.
5. **계정은 어디에도 남지 않는다** → API는 선택자만 받고(`password` 키 거부), 보고서·CSV·캡처에 계정 문자열이 없음을 테스트가 확인.
6. **검사 못 한 것은 정상도 버그도 아니다** → BLOCKED/ERROR는 재검, 회귀에서 누락은 해결로 치지 않음.

## 현재 미완성과 다음 단계

- **실사이트 기능 시나리오**: "검색어 입력 → 결과 N건", "탭 전환 → 영역 표시" 같은 기대값을 제품별로 등록해야 기능 FAIL이 자동으로 나온다. 지금은 스모크와 조건 계약까지.
- **AI 레이어**: 엔진은 규칙 기반이다. 계획은 LLM이 페이지 요약을 보고 "다음 동작 + 기대 결과"를 제안하고, 실행은 지금의 정책 가드를 통과시키며, 결과는 같은 검증식 포맷으로 남기는 탐색 에이전트. 발견 목록·정책·검증식 포맷이 이미 분리되어 있어 그 위에 얹을 수 있다.
- **시각 비교 정밀화**: 뷰포트 전체 → 컴포넌트 단위 영역 기본 제공, 레이아웃(겹침·잘림) 판정.
