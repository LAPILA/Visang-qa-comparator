# 검사 실행 로그인 모드 요청사항

## 목적

검사 실행 화면에서 **로그인 검사**와 **비로그인 검사**를 명시적으로 선택한다. 선택한 모드에 따라 페이지 탐색 중 로그인 화면을 처리하는 방식이 달라야 한다. 프로젝트 설정에 저장한 환경별 로그인 URL·ID·비밀번호를 로그인 검사에 사용할 수 있어야 한다.

## 검사 실행 화면

1. 검사 설정에 `인증 상태` 선택 옵션을 추가한다: `로그인` / `비로그인`.
2. 선택값은 실행 시작 전 화면에 보이고, 실행 설정 사본과 최종 보고서에 기록한다. A/B 비교에서는 각 환경에 같은 모드를 적용하되, 실제 로그인 성공 여부는 환경별로 따로 기록한다.
3. `로그인`을 선택했는데 대상 환경의 로그인 정보가 없으면 시작 전에 부족한 항목을 알려준다. 필요한 값이 무엇인지는 대상 사이트의 로그인 방식에 맞춰 확인한다.

## 로그인 검사 동작

1. 탐색 중 로그인 버튼이나 로그인 페이지를 발견하면 해당 환경의 로그인 절차를 **우선 수행**한다. 로그인 후 원래 검사하려던 페이지로 돌아가 검사를 계속한다.
2. 로그인 버튼의 존재만으로 성공 처리하지 않는다. 로그인 폼 제출 후 실제 인증 상태를 확인하고, 성공·실패·추가 인증 필요를 구분한다.
3. 자동으로 처리할 수 없는 CAPTCHA, 2단계 인증, 약관 동의 등은 사용자의 수동 진행을 기다리거나 `BLOCKED`로 기록한다. 무한 재시도나 임의의 우회는 하지 않는다.
4. 환경별로 로그인 시도 횟수와 대기 시간을 제한한다. 로그인 후에도 다시 로그인 페이지로 이동하면 세션 만료 또는 로그인 실패로 기록하고 원인을 남긴다.

## 비로그인 검사 동작

1. 로그인 버튼을 검사 목적으로 클릭하거나 저장된 계정 정보를 사용하지 않는다.
2. 링크나 리다이렉트로 로그인 페이지에 도달하면 직전 검사 페이지로 돌아가 탐색을 이어간다. 로그인 페이지 자체와 되돌아간 사실은 방문 경로에 기록한다.
3. 되돌아갈 페이지가 없거나 다시 로그인 페이지로 반복 이동하면 해당 경로를 `BLOCKED` 또는 `SKIP`으로 표시하고 다음 대상 페이지로 넘어간다. 같은 경로를 무한히 왕복하지 않는다.
4. 로그인해야만 볼 수 있는 기능을 비로그인 모드에서 `PASS`로 판정하지 않는다. 접근 제한 화면이나 로그인 유도 화면은 관찰 결과와 증거로 남긴다.

## 기록과 검증 기준

- 실행 기록에 선택 모드, 환경별 로그인 시도·성공 여부, 로그인 화면으로 이동한 URL, 원래 페이지, 복귀 결과, 차단 사유를 남긴다.
- 로그인 모드에서는 인증이 필요한 대표 페이지에 실제로 접근한 뒤 검사가 진행되는지 확인한다.
- 비로그인 모드에서는 로그인 페이지로 이동한 뒤 이전 페이지로 복귀하고, 동일 경로를 반복하지 않으며, 미검사 기능이 성공으로 집계되지 않는지 확인한다.
- 비밀번호·쿠키·세션 토큰은 보고서, 스크린샷 설명, 로그, 공유 SQL에 기록하지 않는다.

## 구현 상태 (v0.5.0, taehwan- × 1105_mia 통합)

| 요청 | 상태 | 구현 |
|---|---|---|
| 검사 설정의 `인증 상태` 선택 (로그인/비로그인) | 구현 | 1단계 라디오: 비로그인 · 로그인 · 수동 로그인. API `authMode`, 실행 설정 사본(`job.options.auth_mode`)과 보고서 `manifest.auth.mode`에 기록 |
| A/B 같은 모드, 로그인 성공은 환경별 기록 | 구현 | `manifest.auth.loggedIn.{a,b}`, 시작 행의 `a.login`/`b.login` 검증식 |
| 로그인 정보 없으면 시작 전 안내 | 구현 | UI 시작 전 검사 + 서버 `require_login_credentials`(없는 환경 이름을 알려 주고 400) |
| 프로젝트 설정의 환경별 로그인 URL·ID·PW 사용 | 구현 | `credentialRefs`(ID만 전송) → `qa/secrets.py`가 `qa/projects_db.environment_credentials`로 서버에서 복호화 |
| 로그인: 성공·실패·추가 인증 구분 | 구현(기존) | `TEST_ACCOUNT_LOGIN_OK` / `LOGIN_FAILED` / `LOGIN_FORM_NOT_FOUND` / `LOGIN_CREDENTIALS_MISSING`; CAPTCHA·2단계 인증은 성공 근거가 없어 BLOCKED, 우회·무한 재시도 없음 |
| 로그인: 탐색 중 로그인 화면 → 재로그인 후 원래 페이지 | 구현 | 환경당 최대 2회 재로그인, 성공 `RELOGIN_OK`, 실패 `LOGIN_SESSION_LOST`(BLOCKED) |
| 비로그인: 로그인 버튼·계정 사용 안 함 | 구현 | 계정을 읽지 않음, 로그인 링크 `LOGIN_LINK_ANONYMOUS`, 로그인 버튼 `LOGIN_ACTION_NOT_SMOKED` |
| 비로그인: 로그인 화면 도달 → 직전 페이지로 복귀, 기록 | 구현 | `LOGIN_REQUIRED_ANONYMOUS`(SKIP) + 캡처, `actual.returnTo` = 링크가 있던 페이지, 그 화면의 링크는 따라가지 않음. 같은 URL은 한 번만 방문 |
| 로그인 필요 기능을 PASS로 집계하지 않음 | 구현 | 해당 행 SKIP → 검수 분류 미실행(NOT_RUN) |
| 비밀번호·쿠키·토큰을 보고서·로그·공유 SQL에 미기록 | 구현 | 테스트 `tests/test_projects_and_auth.py`가 보고서 직렬화에서 계정 문자열 부재를 확인 |
| `수동 로그인` 옵션과의 관계 정리 | 구현 | 수동 로그인은 인증 상태의 세 번째 선택지. 서버가 `authMode` 하나로 정규화 |
| 로그인 버튼·폼 선택자, 성공 판정 기준 별도 설정 | 구현(기존) | 4단계 로그인 폼 선택자(비우면 자동 탐지), `successSelector`/`failureSelector` |
| 로그인 후 새 탭이 열리는 사이트 | 미구현 | 같은 탭 로그인만 지원. 새 탭 로그인은 수동 로그인 사용 |

## 구현 시 확인할 사항

- 사이트별 로그인 버튼·폼 선택자와 로그인 성공 판정 기준은 별도 설정이 필요하다. 버튼만 발견했다고 무조건 클릭하지 말고, 승인된 로그인 동작인지 확인한다.
- 로그인 전후에 URL이 바뀌거나 새 탭이 열리는 경우에도 원래 검사 페이지로 복귀할 수 있어야 한다.
- 현재의 `수동 로그인` 옵션과 새 `로그인/비로그인` 선택값의 관계를 정리해 화면에서 중복되거나 모순된 설정을 선택하지 않도록 한다.
